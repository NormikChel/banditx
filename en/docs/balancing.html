An upstream is a pool of identical backends plus rules: how to pick, how to check, what to do on failure.

#Selection strategies

StrategyWhen to use
round_robindefault when backends are identical
least_connwhen requests have different durations (SSE, streaming)
randommany backends, doesn't matter who takes the next
ip_hashclient-to-backend affinity without cookies
uri_hashwhen you need the same cache hit
p2cpower of two choices — nearly always best p99
✓If in doubt

Pick p2c. It's nearly as good as least_conn and resilient to skew.

#Weights and backup

Heterogeneous machines can be loaded unevenly via weight. Some servers can be backup: true — they take over only if every primary is down.

#Sticky sessions

When a backend keeps state in memory (sessions, cache), you need client affinity. banditx supports two modes: cookie and IP.

#Health checks

Active checks are HTTP probes to each backend at a fixed interval. Passive checks watch real traffic (5xx, timeouts).

ℹactive + passive

Combine both. Active catches a dead process; passive catches degradation under load, when /healthz returns 200 but real requests fail.

#Circuit breaker

When a backend starts failing consistently, the breaker stops sending traffic for a fixed time. Neighbors in the pool are saved from cascading failure.

#Retries and timeouts

Retries are safe only for idempotent requests. banditx retries GET, HEAD, OPTIONS, PUT, DELETE automatically. POST — only if the backend sent zero bytes.

#Keep-alive pool

Connection reuse to the backend is the cheapest way to boost RPS. On by default, but tune pool size for load.
